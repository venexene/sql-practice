# List the Products Ordered in a Period

## Инсайт

Нужно посчитать не количество заказов, а суммарное число заказанных единиц каждого товара за февраль 2020 года. Поэтому строки сначала ограничиваются нужным периодом, затем группируются по товару и фильтруются по итоговой сумме.

Название товара находится в `Products`, а дата и количество единиц - в `Orders`, поэтому перед агрегацией таблицы нужно соединить по `product_id`.

## Решение

### JOIN + фильтрация периода + GROUP BY

```sql
SELECT p.product_name, SUM(o.unit) AS unit
FROM Products p
JOIN Orders o
ON p.product_id = o.product_id
WHERE '2020-02-01'::date <= o.order_date
  AND o.order_date < '2020-03-01'::date
GROUP BY p.product_name
HAVING SUM(o.unit) >= 100;
```

`JOIN` связывает заказ с названием товара. `WHERE` оставляет только заказы февраля, `GROUP BY` собирает их по товару, а `SUM(o.unit)` вычисляет общее количество заказанных единиц. `HAVING` оставляет товары с итогом не меньше 100.

## Почему используется SUM, а не COUNT

Одна строка в `Orders` может содержать несколько единиц товара. `COUNT(*)` посчитал бы количество записей о заказах, но не количество заказанных единиц.

Например:

| product | unit |
|---|---:|
| A | 40 |
| A | 70 |

Для товара `A` существует две строки заказа, но суммарно заказано `110` единиц. Условию задачи соответствует `SUM(unit) = 110`, а не `COUNT(*) = 2`.

## Полуоткрытый диапазон дат

Период записан так:

```sql
'2020-02-01'::date <= o.order_date
AND o.order_date < '2020-03-01'::date
```

Левая граница включает 1 февраля, а правая исключает 1 марта. Такой диапазон охватывает весь февраль и не требует вручную указывать последний день месяца.

Подход остаётся безопасным и в случае, если колонка позднее станет содержать не только дату, но и время: все значения до начала марта продолжат попадать в период.

## WHERE и HAVING выполняют разные задачи

- `WHERE` фильтрует отдельные строки заказов до группировки. Заказы из других месяцев не участвуют в сумме.
- `HAVING` фильтрует уже сформированные группы по результату `SUM(o.unit)`.

Перенести условие `SUM(o.unit) >= 100` в `WHERE` нельзя, потому что агрегат ещё не вычислен на этом этапе.

## Почему достаточно JOIN

В ответе нужны только товары, у которых есть заказы в указанном периоде. Товары без совпадений не могут набрать 100 единиц, поэтому сохранять их через `LEFT JOIN` не требуется.

Кроме того, фильтр по `o.order_date` всё равно относится к строкам таблицы `Orders`, поэтому внутреннее соединение прямо отражает смысл запроса.

## Пограничные случаи

- Товар с суммой ровно `100` попадает в результат благодаря оператору `>=`.
- Заказы до 1 февраля и начиная с 1 марта не учитываются.
- Несколько заказов одного товара складываются независимо от количества строк.
- Товар без февральских заказов не появляется в результате.
- Итоговая сортировка условием задачи не требуется.

## Что важно запомнить

- **Сначала ограничивается период.** В агрегацию должны попасть только февральские заказы.
- **SUM считает единицы товара.** COUNT считал бы строки заказов и дал бы другой смысл.
- **WHERE работает до группировки.** Он отбирает исходные записи.
- **HAVING работает после группировки.** Он проверяет суммарное значение группы.
- **Полуоткрытый диапазон удобен для календарных периодов.** Начало следующего месяца служит верхней границей.
- **Обычного JOIN достаточно.** Товары без подходящих заказов не могут пройти условие по сумме.
