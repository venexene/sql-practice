# Friend Requests II: Who Has the Most Friends

## Инсайт

Каждая строка `RequestAccepted` описывает одну дружбу между двумя людьми. Для подсчёта друзей направление заявки уже не важно: отправитель и получатель являются равноправными участниками связи.

Поэтому идентификаторы из `requester_id` и `accepter_id` нужно привести к одной колонке, сохранить все их появления, а затем посчитать количество строк для каждого человека.

## Решение

### UNION ALL + GROUP BY

```sql
SELECT id, COUNT(*) AS num
FROM (
    (SELECT requester_id AS id
    FROM RequestAccepted)
    UNION ALL
    (SELECT accepter_id AS id
    FROM RequestAccepted)
)
GROUP BY id
ORDER BY num DESC
LIMIT 1;
```

Первая часть возвращает всех отправителей, вторая - всех получателей. После `UNION ALL` каждая дружба представлена двумя строками: по одной для каждого участника. `GROUP BY id` собирает появления одного человека, а `COUNT(*)` вычисляет количество его друзей.

Сортировка по убыванию `num` ставит человека с наибольшим числом друзей первым, после чего `LIMIT 1` оставляет его в результате.

## Почему нужен UNION ALL

Повторения идентификатора несут смысл: каждое появление соответствует ещё одной дружбе человека. Например, для связей `(1, 2)` и `(1, 3)` объединённый набор должен содержать две строки с `id = 1`.

`UNION` удалил бы одинаковые значения и превратил обе строки в одну, из-за чего количество друзей было бы посчитано неверно. `UNION ALL` ничего не удаляет и сохраняет данные, необходимые для последующей агрегации.

## Почему учитываются обе колонки

Если считать только `requester_id`, будут учтены лишь друзья, которым человек сам отправлял заявки. Если считать только `accepter_id`, потеряются друзья из принятых другими пользователями заявок.

Объединение обеих колонок делает связь ненаправленной для целей подсчёта:

| requester_id | accepter_id | Вклад в подсчёт |
|---:|---:|---|
| 1 | 2 | один друг для 1 и один друг для 2 |
| 1 | 3 | один друг для 1 и один друг для 3 |

В результате человек 1 встречается два раза и получает `num = 2`.

## Почему достаточно LIMIT 1

После `ORDER BY num DESC` первой становится строка с максимальным количеством друзей. По условию задачи такой человек только один, поэтому дополнительное правило разрешения ничьей не требуется.

Если бы несколько человек могли делить первое место и требовалось вернуть их всех, одного `LIMIT 1` было бы недостаточно.

## Замечание о подзапросе

В PostgreSQL 16 и новее производный подзапрос может не иметь псевдонима, поэтому текущая запись допустима. Для совместимости с более ранними версиями PostgreSQL и другими СУБД после закрывающей скобки обычно задают псевдоним.

Скобки вокруг каждого отдельного `SELECT` внутри `UNION ALL` здесь не обязательны, но корректности не мешают.

## Что важно запомнить

- **Дружба учитывается для обоих участников.** Нужно обработать и `requester_id`, и `accepter_id`.
- **UNION ALL сохраняет повторения.** Здесь повторы используются для подсчёта количества связей.
- **UNION применять нельзя.** Удаление одинаковых идентификаторов исказит число друзей.
- **После объединения задача становится обычной агрегацией.** `GROUP BY id` и `COUNT(*)` считают появления каждого человека.
- **Направление заявки не влияет на дружбу.** Обе исходные колонки приводятся к общей колонке `id`.
- **LIMIT 1 опирается на гарантию уникального победителя.** При возможной ничьей потребовалась бы другая логика.
