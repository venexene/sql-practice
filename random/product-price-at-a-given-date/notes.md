# Product Price at a Given Date

## Инсайт

Цена товара на 16 августа 2019 года определяется последним изменением не позднее этой даты. Если подходящих изменений нет, действует начальная цена `10`.

Нужно решить две разные задачи: найти последнюю допустимую дату изменения и сохранить полный список товаров, включая те, у которых изменения были только позже нужной даты. Затем можно получить цену из соответствующей записи или выбрать значение по умолчанию.

## Решение

### MAX по отфильтрованным датам + LEFT JOIN + получение цены

```sql
SELECT DISTINCT p1.product_id, CASE WHEN p2.max_date IS NULL THEN 10 ELSE p1.new_price END AS price
FROM Products p1
JOIN (
    SELECT DISTINCT pd.product_id, pm.max_date
    FROM Products pd
    LEFT JOIN (
        SELECT product_id, MAX(change_date) AS max_date
        FROM Products
        WHERE change_date <= '2019-08-16'::date
        GROUP BY product_id
    ) pm ON pd.product_id = pm.product_id
) p2 ON p1.product_id = p2.product_id AND (p1.change_date = p2.max_date OR p2.max_date IS NULL);
```

## Как устроены этапы

1. **Найти последнюю допустимую дату.** Подзапрос `pm` сначала исключает изменения после 16 августа, затем вычисляет `MAX(change_date)` отдельно для каждого товара.
2. **Сохранить все товары.** `pd` берётся из полной истории `Products`. `LEFT JOIN` добавляет найденную дату, а для товаров без подходящих изменений оставляет `NULL`. Внутренний `DISTINCT` превращает повторяющиеся записи истории в одну пару «товар - последняя дата».
3. **Вернуть цену.** Внешнее соединение выбирает запись `p1` с найденной датой. Если дата отсутствует, условие допускает любые записи этого товара, а `CASE` возвращает для них `10`. Внешний `DISTINCT` убирает одинаковые ответы.

## Почему внешний DISTINCT здесь нужен

Если `max_date` найдена, соединение по товару и дате выбирает одну запись: пара `product_id` и `change_date` является первичным ключом.

Если `max_date` равна `NULL`, условие `OR p2.max_date IS NULL` пропускает все записи истории этого товара. Для каждой из них `CASE` возвращает одну и ту же цену `10`. Без внешнего `DISTINCT` товар мог бы появиться в результате несколько раз.

## Граничные случаи

- Изменение ровно 16 августа учитывается благодаря `<=`.
- Из нескольких изменений до нужной даты выбирается самое позднее, а не самая высокая цена.
- Изменения после нужной даты не влияют на выбранную цену.
- Если все изменения товара произошли позже нужной даты, товар остаётся в результате с ценой `10`.

## Что можно упростить

Можно сначала сформировать отдельный список уникальных товаров, затем получить записи последних допустимых изменений и присоединить их к этому списку через `LEFT JOIN`. Такой подход позволяет избежать соединения со всей историей в ветке без подходящей даты и последующего удаления повторных ответов.

Другой вариант - ранжировать допустимые изменения каждого товара оконной функцией по убыванию даты. При этом полный список товаров всё равно нужен, чтобы не потерять товары без подходящих изменений.

## Что важно запомнить

- **Сначала ограничить даты, затем искать максимум.** Глобально последнее изменение товара может произойти уже после нужной даты.
- **MAX даты и MAX цены отвечают на разные вопросы.** Цена может снижаться; нужно значение из последней подходящей записи, а не максимальная цена.
- **Фильтр истории не должен уничтожать список товаров.** Поэтому поиск допустимых изменений выполняется отдельно от набора всех товаров.
- **NULL в max_date означает отсутствие подходящего изменения.** В этом случае выбирается начальная цена, а не исключается товар.
- **Связь по товару и дате возвращает согласованные данные.** Цена берётся из той строки, которой принадлежит выбранная дата.
- **Роль DISTINCT зависит от структуры соединения.** Здесь оба удаления повторов имеют конкретную причину, а не добавлены на всякий случай.
- **Паттерн «последняя запись не позже даты» применим к истории изменений.** Он встречается в задачах о ценах, тарифах и статусах.
- **Сортировка по условию не требуется.** Товары можно вернуть в любом порядке.
